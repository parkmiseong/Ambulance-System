# 배경 구급차 원본 경로 검증 (2026-11-17)

원본 `SUMO/강남/ambulance_routes.rou.xml`의 차량 180대를 해당 `osm.net.xml.gz`에 대해 읽기 전용으로 검사했습니다. SUMO 시뮬레이션·모델 학습·자동 경로 수정·원본 파일 변경은 수행하지 않았습니다.

| 항목 | 결과 |
|---|---:|
| 원본 차량 정의 | 180대 |
| 정적 검증 정상 / 문제 차량 | 73 / 107대 |
| 고유 경로 정상 / 문제 | 9 / 14개 |
| 전체 고유 경로 | 23개 |
| 여러 차량이 공유하는 경로 그룹 | 9개 |
| 고유 경로 외 추가 중복 차량 정의 | 157개 |
| 존재하지 않는 edge가 포함된 차량 | 0대 |
| 연속 edge의 junction이 인접하지 않은 차량 | 0대 |
| emergency 허용 차로가 없는 edge를 지나는 차량 | 103대 |
| 연속 edge 사이 차로 connection이 없는 차량 | 10대 |
| 출발 edge에 emergency 허용 차로가 없는 차량 | 39대 |

문제 유형별 인원은 중복되므로 합산하시면 안 됩니다. 경로 공유 자체는 오류가 아닙니다. 일반 edge 내부에서 허용되는 차선 변경을 포함한 위상적 연결 가능성을 검사했으며, 실제 차량이 주어진 거리 안에서 차선 변경에 성공하는지는 판단하지 않았습니다.

별도 SUMO 1.28.0의 `duarouter.exe`에서도 `--ignore-errors false --repair false --repair.from false --repair.to false --skip-new-routes true`로 원본을 검증했습니다. 종료 코드는 1이며, 거부된 107대의 차량 ID는 정적 검증 결과와 완전히 일치합니다. 진단 출력에는 정상 73대만 기록되었고, 그 경로의 edge 순서가 원본과 같음을 확인했습니다. 이 진단 출력은 학습 입력으로 연결하지 않았습니다.

예를 들어 60대가 공유하는 `46709879 → 65369551#0 → 1336765175#0 ...` 경로에는 긴급차 불허 edge가 있습니다. 4대가 공유하는 `-454158885#0 → 454158885#0` 반복 경로에는 해당 차로 connection이 없습니다.

이 수치는 원본 차량 정의 180대에 대한 집계입니다. 실제 시나리오 9는 교통 scale 0.8을 사용하므로 실제 삽입 차량 수와 같다는 뜻은 아닙니다. 문제 입력이 확인되었지만, 이것만으로 이번 27회차의 native NULL 포인터 충돌 원인을 확정할 수는 없습니다.

원본 network·route 파일의 SHA256은 실행 전후 동일했습니다. 핵심 증거는 [요약 JSON](audit_summary.json), [차량·경로별 상세 결과](static_route_audit.json), [duarouter 명령과 종료 코드](duarouter_strict.json), [native 오류 로그](duarouter_strict_errors.log)입니다. [검사 스크립트](audit_routes.py)는 검증 절차 보관용이며, 이미 있는 증거 JSON을 덮어쓰지 않도록 새 출력 파일 생성을 요구합니다.
