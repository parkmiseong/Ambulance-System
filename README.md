# Ambulance-System
## 연구 개발 및 필요성
구급차가 환자를 어느 병원으로 이송할지 결정하는 문제는 병상 가용성, 이동 시간, 병원 별 치료 역량 등 복합 요인을 고려해야 하는 순차적 의사 결정 문제로, 단순 최단 거리 기반 이송은 최적이 아니라는 점이 보고되어 있어, 강화 학습 기반 정책 학습으로 고도화 연구 개발 필요

## 주요 연구 내용
- State : 환자·대기열·운행 임무 요약, 병원별 병상·이동시간 / Action : 이송 병원 선택 / Reward : 도착·실패, 대기 포함 총 시간, 병원 적합도·점유율
- 최단 거리•규칙 기반 baseline 대비 RL 정책의 개선 효과 검증
- 공개 데이터 또는 시뮬레이션 환경 기반 학습 환경 구축

## 연구 진행 내용

### baseline 의사결정 기준
- 최단거리 : route length 최소
- 최단시간 : 예상 travel time 최소
- 병상기반 : occupancy + 적합도
- 치료역량 : 환자 적합도
- 종합휴리스틱 : 시간 + 병상 + 적합도
- DQN : 학습된 Q-value

### 실험 로그에 저장되는 정보
- logged_at : 실행 시간과 시간, 시간대
- run_id : 각 실행을 구분하는 고유 ID
- run_type : 학습 또는 평가
- record_type : 실행 시작, 에피소드, 환자별 결과, 실행 종료 등

- scenario_id : 환자 발생 확률과 배경 교통량 조합의 시나리오 번호

### 현재 MDP 모델링과 의사결정 범위 (v5, 보상 버전 4)

현재 구현은 **여러 구급차가 동시에 운행하는 시스템에서, 다음 배정 환자의
이송 병원을 순차적으로 선택하는 단일 에이전트 문제**다. 구급차마다 별도
에이전트를 두지 않으며, 환자 우선순위와 차량 운행 경로는 규칙과 SUMO가 처리한다.

개념적인 모델은 `M = (S, A, P, R, gamma)`로 표현한다. 전체 시스템 상태 `S`에는
모든 차량 위치·교통 상태, 대기 환자, 운행 임무, 병원 예약·치료·반환 일정 등이
포함된다. 실제 DQN 입력은 이를 요약한 관측 `o = phi(S)`다. 개별 운행 임무의
환자·목적지·위치 등을 모두 관측에 포함하지 않으므로 **완전한 Markov 상태를
보장하지 않는 부분 관측 기반 근사 모델**이다.

| 구성 | 현재 구현 |
|---|---|
| 에이전트 | 시스템 전체의 병원 배정을 담당하는 DQN 1개 |
| 의사결정 시점 | 빈 구급차에 배정할 환자와 유효 병원 후보가 있을 때 |
| 관측 | 환자·시간·대기열·운행 임무 요약 16개 + 병원별 특징 9개 |
| 행동 | 유효 병원 중 하나의 인덱스 선택 |
| 상태 전이 | 환자 발생, 배정·병상 예약, SUMO 이동, 도착·실패, 병상 반환 |
| 보상 | 선택 사이에 관측된 환자별 결과 보상의 합; 아래 보상 절 참조 |
| 할인율 | `gamma = 0.95`, 병원 선택 전이 한 번마다 적용 |
| 종료 | 환자 발생 종료 후 모든 환자의 도착·실패 확정, 또는 안전 종료 경계 |

배정 대기, 병원 선택 보류, 환자 우선순위 변경은 DQN의 행동에 포함되지 않는다.
기본 대기열은 KTAS 숫자가 작은 환자 우선이며, 같은 중증도는 발생 시각 순이다.
`fifo`, 대기시간에 따라 우선순위를 높이는 `hybrid`도 별도 설정할 수 있다.

#### 상태·관측 벡터

병원 수를 `H`라 하면 v5 입력 차원은 `16 + 9H`다. 실제 병원 7개와 가상 병원 2개를
사용하는 현재 설정은 **97차원**이다. 기존 v3/v4 모델은 `15 + 9H`, 96차원을 유지한다.
앞의 15개 공통 특징은 같으며 v5에서 인덱스 15의 특징 한 개만 추가한다.

| 공통 인덱스 | 관측 내용 | 입력 값 |
|---|---|---|
| 0~1 | 환자 도로 시작 노드의 SUMO x, y 좌표 | 각 좌표 / 10,000 |
| 2 | 환자 KTAS | KTAS / 5 |
| 3 | 현재 환자의 배정 대기시간 | 대기시간 / `max_wait` |
| 4 | 현재 시뮬레이션 시각 | 시각 / `drain_deadline` |
| 5 | 남은 환자 발생 기간 | `max(0, arrival_steps - 시각) / arrival_steps` |
| 6 | 운행 중 임무 수 | 임무 수 / 구급차 한도 |
| 7 | 대기 환자 수 | 환자 수 / 100 |
| 8~12 | KTAS 1~5별 대기 환자 수 | 각 환자 수 / 100 |
| 13 | 대기열에서 가장 오래 기다린 시간 | 시간 / `max_wait` |
| 14 | 운행 중 임무의 남은 이송 제한시간 평균 | 평균 / `mission_timeout`; 운행이 없으면 0 |
| 15 | 운행 중 임무들의 배정 당시 예상 환자 보상 합 | 예상 보상 합 / 100; 운행이 없거나 `--pending-reward-feature zero`이면 0 |

병원 `h`의 블록은 v5에서 `16 + 9h`부터 시작한다(v3/v4는 `15 + 9h`). 병원 순서는
manifest로 고정한다.

| 블록 내 인덱스 | 병원별 관측 내용 | 입력 값 |
|---|---|---|
| 0 | 교통을 반영한 예상 이동시간 | `min(예상 초 / 600, 5)` |
| 1 | 배경·예약·치료 중 병상을 합한 점유율 | 점유율 그대로 |
| 2 | 병원 역량 특징 | 권역센터 1.0, 지역센터 0.8, 지역기관 0.6, 그 외 0.3 |
| 3 | 현재 환자와 병원의 적합도 | 아래 적합도 표의 불확실성 반영 기대값 |
| 4 | 예약 병상량 | 예약 건수 × `bed_fraction` |
| 5 | 치료 중 병상량 | 치료 중 환자 수 × `bed_fraction` |
| 6 | 다음 치료 병상 반환까지의 시간 | `min(남은 초 / treatment_seconds, 1)`; 반환 일정이 없으면 0 |
| 7 | 경로 도달 가능 여부 | 가능 1, 불가 0 |
| 8 | 환자 1명 추가 예약 가능 여부 | 가능 1, 불가 0 |

대기열 통계는 현재 선택 중인 환자를 대기열에서 꺼낸 뒤 계산한다. 정규화가
모든 입력을 `[0, 1]`로 제한하는 것은 아니며, 대기 환자 수/100 등은 1을 넘을 수 있다.

#### 행동과 유효 행동 마스크

행동 공간은 `A = {0, ..., H-1}`이다. 실제 선택은 다음 조건을 모두 만족하는
유효 집합 `A_valid(o)` 안에서만 수행한다.

- 환자 발생 도로에서 병원 접근 도로까지 구급차 경로가 존재한다.
- 병원 종류가 현재 KTAS에 필요한 역량을 충족한다.
- 점유율이 유한하고 0 이상, 기본 상한 0.85 미만이다.
- 환자 1명 예약을 추가해도 점유율이 상한을 넘지 않는다(`can_admit`).
- 병원이 수용 가능한 상태다(`accepting`이 명시적으로 꺼져 있지 않음).

| 환자 KTAS | 최소 수용 역량: 코드의 hard mask |
|---|---|
| 1, 2 | 권역응급의료센터 |
| 3 | 지역응급의료센터 이상 |
| 4, 5 | 등록된 4종 병원 모두 |

이 조건은 연구용 필터이며 실제 임상 이송 지침을 의미하지 않는다. 위 역량 제약과
상태 벡터의 수치형 역량 특징은 별개다. 예를 들어 적합도 표에서 점수가 있더라도
hard mask에 걸리는 병원은 선택할 수 없다.

일시적인 병상 부족만 해결하면 수용 가능한 병원이 있으면, 환자를 대기열로
돌려보내 `min(30초, treatment_seconds)` 뒤 재시도한다. 경로·역량·수용 여부 등으로
유효 병원이 없으면 미배정 실패로 확정한다. 빈 구급차가 없으면 대기열에서 기다린다.

#### 전이·환자 발생·종료 조건

SUMO 시계는 기본 1초씩 진행하지만 병원 선택은 불규칙한 시점에 발생하며,
같은 시뮬레이션 시각에 여러 번 선택할 수도 있다. 매 에피소드에서 발생 확률
`{0.2, 0.3, 0.4}`와 배경 교통량 배율 `{0.3, 0.5, 0.8}`의 9개 조합을 순환한다.

```text
매초 환자 발생 확률 = 시나리오 기본 확률 × demand_scale × 커리큘럼 배율
```

기본 첫 500초 동안 매초 최대 1명이 발생한다. 검증된 도로에서 위치를 선택하고,
KTAS 1~5를 각각 20% 확률로 생성한다. `pre_ktas`는 생성된 KTAS와 같은 값이다.
학습 에피소드 시드는 기본 `seed + 10000 + 누적 에피소드 번호`이며, 발생 여부와
환자 속성의 난수 스트림을 분리해 부하를 바꿔도 같은 시드의 공통 환자 속성을 유지한다.

병원 초기 배경 점유율은 에피소드 시드에 따라 20~60%에서 생성하고 고정한다.
선택 즉시 환자 1명분(기본 점유율 0.08)을 예약하며, 도착하면 치료 중 병상으로
전환하고 기본 900초 후 반환한다. 이송 실패 시 예약은 반환한다.
환자 위치에서 구급차를 생성해 병원까지 운행하므로 **차고지→현장 출동, 현장 처치,
병원→차고지 복귀 및 차량별 재배치는 모델링하지 않는다.**

환자 발생이 끝나도 대기·운행 중인 환자가 있으면 계속 처리한다. 기본 배정 대기
제한은 발생 후 1,800초, 이송 제한은 배정 후 1,800초다. 이송 제한은 배정 시점부터
별도로 보장한다. 안전 종료 경계는 다음과 같다.

```text
drain_deadline = arrival_steps + max_wait + mission_timeout + 2
              = 500 + 1800 + 1800 + 2 = 4102초 (기본 설정)
```

모든 환자가 도착하거나 운영상 실패로 확정되면 에피소드를 종료한다. 안전 경계에
남은 환자는 `censored`로 구분한다. 생존·사망이나 실제 치료 결과는 시뮬레이션하지
않으며, `arrived`는 선택 병원까지의 이송 완료를 의미한다.

### 현재 보상 함수 설계 (v4)

구현은 [reward.py](CODE/reward.py), 적용 시점은 [simulation.py](CODE/simulation.py)의
`finish()`다. 성공한 환자의 원래 보상은 다음 항목의 합이다.

```text
T   = 환자 발생부터 병원 도착까지 총 소요 시간 = 배정 대기 + 이송 시간
L_k = KTAS k별 연구용 골든타임
x   = T / L_k
f   = 중증도 불확실성을 반영한 병원 적합도 (0~1)
o   = 병원 선택 직전 점유율을 [0, 1]로 제한한 값
n   = rejection_count (현재 공통 시뮬레이션에서는 전달하지 않아 기본 0)

r_success = 10 × I(T <= L_k)
            - 4 × min(x, 3)
            - 8 × min(max(x - 1, 0), 2)
            - 24 × (1 - f)^2
            - 8 × o
            - 5 × max(o - 0.7, 0) / 0.3
            - 12 × n
```

`I`는 조건을 만족하면 1, 아니면 0이다. 함수 인자 이름 `travel_time`에는 현재
공통 엔진이 **이동시간만이 아니라 배정 대기를 포함한 총 시간**을 전달한다.
`travel_seconds` 로그는 배정 후 이동 구간만을 뜻하므로 두 값을 구분해야 한다.

| 보상 항목 | 목적 | 기본 가중치·제한 |
|---|---|---|
| 골든타임 보너스 | 목표 시간 내 병원 도착 | +10, 성공한 경우만 |
| 소요 시간 벌점 | 총 대응시간 단축 | -4 × 시간 비율, 최대 -12 |
| 초과 시간 벌점 | 골든타임 초과 억제 | -8 × 초과 비율, 최대 -16 |
| 병원 부적합 벌점 | 중증도에 맞는 병원 선택 | -24 × 적합도 부족의 제곱 |
| 점유율 벌점 | 선택 당시 병원 부하 반영 | -8 × 점유율 |
| 과밀 벌점 | 점유율 70% 초과 병원 집중 억제 | 기본 최대 -5 |
| 수용 거절 벌점 | 별도로 주어진 거절 횟수 반영 | -12 × 횟수; 현재 엔진은 0 |

후보 병원이 마스크에서 제외되는 횟수나 병상 부족 재시도 횟수를 `n`으로
자동 누적하지는 않는다. 골든타임과 적합도·가중치는 모두 연구용 가정값이다.

| KTAS | 1 | 2 | 3 | 4 | 5 |
|---|---:|---:|---:|---:|---:|
| `L_k` (초) | 120 | 180 | 240 | 300 | 360 |

#### 병원 적합도와 중증도 불확실성

불확실성을 반영하기 전 적합도 `SUITABILITY[k][병원 종류]`는 다음과 같다.

| pre-KTAS | 권역응급의료센터 | 지역응급의료센터 | 지역응급의료기관 | 응급실운영신고기관 |
|---|---:|---:|---:|---:|
| 1 | 1.00 | 0.70 | 0.05 | 0.00 |
| 2 | 1.00 | 0.90 | 0.20 | 0.00 |
| 3 | 0.90 | 1.00 | 0.70 | 0.20 |
| 4 | 0.75 | 0.90 | 1.00 | 0.85 |
| 5 | 0.65 | 0.80 | 0.95 | 1.00 |

기본 불확실성은 0.20이다. 관측 중증도에 확률 0.80을 두고 나머지 0.20을
인접 중증도에 균등 분배해 `f = sum(P(k' | pre_ktas) × SUITABILITY[k'][병원])`로
계산한다. 예를 들어 KTAS 3은 `{2: 0.1, 3: 0.8, 4: 0.1}`, KTAS 1은
`{1: 0.8, 2: 0.2}`다. 이 분포는 적합도 계산에만 사용하며 실제 중증도를
재추출하거나 hard mask·골든타임 기준을 확률적으로 바꾸지 않는다.

#### 실패·관측 중단과 버전 차이

v4의 운영상 실패는 미배정·대기 시간 초과·차량 생성 실패·이송 제한 초과·차량
소실 등을 포함한다. 실패 시 성공 보상 항목을 합산하지 않고 다음 값으로 대체한다.

```text
최악 성공 벌점 상한 = 3×4 + 2×8 + 24 + 8 + 5 + 12n = 65 + 12n
실패 벌점          = 위 상한 + 실패 여유 벌점 20 = 85 + 12n
r_failure          = -(85 + 12n) = -85 (현재 n=0)
r_censored         = 0
```

따라서 기본 설정에서는 실패가 늦은 도착보다 높은 환자별 보상을 얻지 않는다.
다만 에피소드 전체에서는 여러 환자의 결과를 합산하므로 개별 성공·실패 개수만으로
정책 순위가 결정되지는 않는다. `censored`의 0은 성공을 의미하지 않으며 결과 미관측을
별도 표시하기 위한 처리다.

기존 v3는 미배정 실패 -20, 배정 후 실패는 시간·적합도·점유율 등의 벌점에 실패
벌점 -20을 더하므로 v4와 점수 체계가 다르다. 기존 모델은 manifest의 보상 버전으로
평가하고, 버전 간 비교는 `--reward-version 4` 등으로 채점 기준을 맞춘다.

#### 환자 보상에서 학습 전이 보상으로의 집계

병원 선택 순서의 인덱스를 `i`라 할 때 경험은 다음처럼 저장한다.

```text
(o_i, a_i, R_i / 100, o_(i+1), done, 다음 상태의 유효 행동 마스크)
R_i = i번째 선택 이후, 다음 선택 직전까지 관측된 모든 환자 결과 보상의 합
학습 목표: E[sum_i gamma^i × (R_i / 100)], gamma = 0.95
```

여러 임무가 겹치므로 `R_i`에는 이전에 배정한 다른 환자의 결과와 미배정 실패도
포함될 수 있다. 다음 선택까지 결과가 없으면 0이고, 같은 시각에 연달아 선택해도
각각 전이를 만든다. 마지막 선택 뒤에 남은 결과는 마지막 전이에 모으며,
**마지막 전이만 `done=True`**로 저장한다. 환자 완료 순서대로 전이를 연결하지 않는다.
첫 선택 전에 확정된 결과는 전체 보고 보상에 포함하지만, 대응 행동이 없으므로
가짜 경험을 만들지 않고 `unattributed_learning_reward`로 구분한다.

v4/v5는 메모리에 저장할 때 보상을 100으로 나눈다. 환자별·에피소드·검증 로그는
원래 보상을 유지한다. 할인은 선택 횟수 기준이며 SUMO 초 또는 선택 사이 경과시간에
따라 바뀌지 않는다. 단순 보상 정규화는 지연된 결과의 기여도 식별 문제를 해결하지
않으며, 이 구조는 이후 별도 실험이 필요한 한계다.

### 현재 학습 알고리즘과 평가 지표

v4/v5는 공통 병원 Q 평가기를 사용하는 masked Double DQN이다. v5는 공통 관측 16개,
해당 병원 특징 9개, 전체 병원 특징의 평균·최소·최대값 27개를 합한 52개 입력에
`128 → ReLU → 128 → ReLU → 1` 평가기를 공유한다. 병원 블록의 순서를 바꾸면
출력 Q값도 같은 순서로 바뀐다. 기존 v4 평가기의 입력은 51개다.
Q값은 개별 환자의 즉시 보상이 아니라 위 학습
목표에 따른 시스템 구간 보상의 할인 누적값을 예측한다.

학습 행동은 epsilon 확률로 유효 후보 중 무작위 선택, 나머지는 유효 후보의
최대 Q값 선택이다. epsilon은 1.0에서 시작해 **실제 학습 업데이트마다** 0.9995를
곱하고 최저 0.05를 유지한다. 메모리 한도는 30,000개, 배치 크기는 32,
Adam 학습률은 0.0005, 손실은 SmoothL1Loss, gradient norm 상한은 5다.
경험이 32개 미만이면 업데이트하지 않으며, 타깃 네트워크는 누적 에피소드 번호가
10의 배수일 때 동기화한다.

```text
a* = argmax_{a in A_valid(o_next)} Q_online(o_next, a)
y  = R_i / 100 + 0.95 × Q_target(o_next, a*)   (비종료 전이)
y  = R_i / 100                               (종료 전이)
```

검증·정책 비교에서는 epsilon=0으로 두고 가중치를 업데이트하지 않는다.
보고하는 환자당 보상은 할인하지 않은 환자별 원래 보상의 합 / 전체 발생 환자 수로,
학습의 할인 누적 목표와 구분한다. 도착률과 골든타임 성공률의 분모도 전체 발생
환자 수이며, `wait`는 실패 환자를 포함한 전체 환자의 평균 배정 대기시간이다.
`censored`는 실패와 별도 집계하되 위 발생 환자 분모에는 포함한다.
최고 모델은 고정 검증 패널 전체 환자의 평균 원래 보상으로 선정한다.

[환자 발생·설정](CODE/experiment_config.py), [병상 전이](CODE/hospital_capacity.py),
[선택 구간 전이](CODE/episode_transitions.py), [DQN](CODE/dqn_agent.py).

### 공통 실행 환경과 이전 실험 버전 3

Python 3.11 가상환경과 별도 SUMO 설치(`SUMO_HOME`)를 사용합니다.
현재 가상환경의 패키지 버전은 `requirements.txt`에 기록했습니다.

`CODE/simulation.py`를 학습·고정 검증·baseline 비교가 공통으로 사용합니다.
모델과 함께 병원 순서/좌표/종류, 네트워크 해시, 검증된 환자 발생 도로,
병원 진입 도로, 병상 설정, 상태 버전, 시드를 manifest에 저장합니다.
평가는 모델의 manifest로 환경을 복원하고, 다른 네트워크는 거부합니다.

병상 점유율은 배정 즉시 예약분을 포함합니다. 도착 시 예약을 치료 중 병상으로
전환하고, 실패 시 예약을 반환합니다. 치료 완료 시 해당 환자의 병상을 반환합니다.
기존 배경 점유율은 고정 부하로 둡니다. 병상 단위 기본 0.08,
치료시간 기본 900초는 실제 병원 통계가 아닌 연구용 가정이며
`--bed-fraction`, `--treatment-seconds`로 변경할 수 있습니다.
일시적인 병상 부족은 재시도하며, 대기 제한 초과 시 실패합니다.
경로·중증도별 병원 역량·수용 여부 제약은 유지합니다.

상태는 환자 위치·중증도 외에 대기시간, 중증도별 대기열, 운행 중 임무,
남은 발생 시간, 병원별 예약·치료 중 병상·다음 병상 반환 시간을 포함합니다.
요약된 관측이므로 전체 시스템의 완전한 Markov 상태를 보장하지는 않습니다.
전이는 병원 선택 순서대로 연결하고 선택 사이의 관측 보상을 합산합니다.
마지막 전이만 종료 처리하며 다음 상태의 유효 행동 마스크도 학습에 사용합니다.
할인은 SUMO 초 단위가 아니라 병원 선택 한 번마다 적용합니다.

전체 환자의 원래 보상(미배정 실패 포함)을 공통 집계하며,
v4에서는 학습 메모리에 저장할 때만 100으로 나눕니다.
도착률과 골든타임 성공률은 발생 환자 전체를 분모로 합니다.
운영상 실패와 실행 종료로 관측이 끊긴 사례(censored)는 별도로 집계합니다.
환자 발생이 끝난 뒤에도 대기 제한 + 출동 제한을 모두 보장하도록 실행합니다.
환자별 로그에는 KTAS, 대기·출동·완료 시각, 운행시간, 병원, 보상, 실패 사유를 남깁니다.

새 상태/병상 모델은 기존 모델과 호환되지 않으며 새로 학습해야 합니다.
v3 파일명은 설정 해시를 포함하므로 기존 v2 모델을 덮어쓰지 않습니다.
`*_last.pth`는 마지막 모델, `*_best.pth`는 고정 검증 패널에서 최고인 모델입니다.
`--eval-every 0`이면 검증과 best 모델 선정을 수행하지 않습니다.
체크포인트는 전체 replay·RNG·최고 검증 점수를 저장하며 동일 설정의
`--resume`만 허용합니다. 검증은 학습 RNG 상태에 영향을 주지 않습니다.
`--episodes`는 이번 실행에서 추가할 횟수입니다. 시작 시 이전 저장 횟수와
목표 누적 횟수, 에피소드마다 누적 번호와 이번 실행 진행률을 표시합니다.
예를 들어 5회 저장된 모델에 `--resume --episodes 100`을 적용하면
`previous=5`, `additional=100`, `target_total=105`가 표시됩니다.
이 학습 횟수 요약은 `--quiet`에서도 표시됩니다.
SUMO 출력도 실행별 `results/sumo/<run_id>/`에 분리합니다.

낮은 부하에서 동작 확인:

```powershell
python CODE/train_agent.py --episodes 1 --eval-every 0 --ambulances 10 --virtual-count 2 --virtual-strategy far --placement-seed 42 --seed 42 --demand-scale 0.1
```

반복되는 SUMO 로딩, 병원 준비, 모델 저장 메시지를 숨기고 에피소드/검증 요약만
보려면 학습 명령에 `--quiet`를 추가합니다.
평가(`run_scenarios.py`)와 대기열 정책 비교(`compare_queue_policies.py`)에도 같은
`--quiet` 옵션을 사용할 수 있습니다.
실행 중에는 1분마다 시뮬레이션 시각과 대기·운행·완료 환자 수를 표시합니다.
검증은 시나리오/시드별 시작과 완료 시간을 표시하며, 검증 전에 체크포인트를
저장하므로 검증 오류 후에도 완료된 학습 에피소드부터 이어갈 수 있습니다.

기존 명령도 지원합니다. `--demand-scale 1`은 기존 발생 확률(시나리오별
0.2/0.3/0.4)을 유지하므로 구급차 10대에 과부하가 생길 수 있습니다.
부하를 낮춰 숨기는 대신 낮은 부하와 과부하를 함께 평가해야 합니다.

같은 환자 스트림·병원 초기 조건으로 여러 시드/부하에서 정책 비교:

### 실험 버전 4: 병원별 공통 Q 평가와 보상 수정

이 절은 v4 도입 시점의 변경입니다. 현재 새 학습은 아래의 v5로 저장합니다.
기존 v3 50회 모델/체크포인트를 덮어쓰지 않습니다.
v3 모델은 기존 네트워크와 보상으로 계속 평가할 수 있지만 v4 학습으로
`--resume`할 수 없습니다. v4는 새로 학습하고 같은 v4 설정끼리 이어갑니다.
같은 설정의 새 실행으로 기존 결과를 덮어쓰려 하면 중단하므로, 이어서 학습할
때는 `--resume`, 독립 실험은 다른 시드나 `--output-root`를 사용합니다.

- v3의 미배정 실패 -20이 늦은 도착보다 유리할 수 있었던 문제를 수정했습니다.
  v4는 기본 가중치에서 모든 운영상 실패를 -85로 평가합니다. 이는 가능한
  성공 벌점의 상한 65에 실패 여유 벌점 20을 더한 연구용 설정입니다.
- 병원마다 별도 출력 편향을 갖던 네트워크 대신, 모든 병원의 특징에 같은
  평가기를 적용합니다. 병원 순서를 바꾸면 Q값도 같은 순서로 바뀝니다.
  이것이 실제 이송 성능 개선을 보장하지는 않으며 별도 비교가 필요합니다.
- v4 학습 메모리의 보상은 원래 보상을 100으로 나눠 저장합니다. 보고되는
  환자별/에피소드 보상은 원래 단위를 유지합니다. Q값과 loss는 학습 단위입니다.
  병원 선택 사이에 결과 보상을 모으는 순차 전이 방식은 유지합니다.
- `--eval-every`가 0보다 크면 마지막 회차도 검증합니다. `0`은 끝까지 검증을 끕니다.
- 에피소드 요약에 시나리오 번호와 기본 발생 확률·배경 교통량을 표시합니다.

부하를 낮은/중간 수준으로 순환하고 두 부하에서 검증하는 초기 실험 예시입니다.
이 부하와 균등 KTAS 분포는 실제 강남구 통계가 아닌 합성 실험 조건입니다.

```powershell
.venv/Scripts/python.exe -u CODE/train_agent.py --episodes 18 --eval-every 9 --ambulances 10 --virtual-count 2 --virtual-strategy far --placement-seed 42 --seed 42 --curriculum 0.1,0.3 --cycle-curriculum --validation-demand-levels 0.1,0.3 --validation-seeds 30001 --trace-decisions --quiet
```

`--cycle-curriculum`은 9개 시나리오마다 다음 부하로 넘어간 뒤 처음 부하로
돌아갑니다. 지정하지 않으면 이전처럼 마지막 부하를 유지합니다.
`--validation-demand-levels`는 커리큘럼 배율과 별개인 절대 `demand_scale` 목록입니다.
최고 모델은 고정 패널 전체 환자 기준 평균 보상으로 선정합니다.

`--trace-decisions`를 학습 또는 `run_scenarios.py`에 추가하면
`experiment_history.csv`의 `decision` 행에 상태, 후보 병원, 유효성/제외 사유,
Q값, 예상 이동시간, 선택 병원과 최단시간 후보의 차이를 저장합니다.
`estimated_patient_reward`는 대기시간과 예상 이동시간으로 계산한 진단용 값이며
실제 반사실적 시뮬레이션 결과나 장기 Q값의 정답이 아닙니다.
기본 실행은 이 상세 추적을 끄며 에피소드 결과에 선택 병원 분포와 평균 추가
예상 이동시간만 남깁니다.

v3와 v4의 원래 보상 점수는 직접 비교하지 않습니다. 기존 v3 모델도
`run_scenarios.py --model <v3파일> --reward-version 4`로 평가하면 고정된 모델의
이송 결과를 v4 보상으로 집계할 수 있습니다. 이 경우에도 모델 가중치는 갱신하지
않습니다. 비교 모델들에 같은 시드·시나리오·부하·보상 버전을 지정하세요.

검토 근거와 남은 제한 사항: [2026-11-09 검토 기록](docs/review_2026_11_09.md).

### 학습 문제를 분리하는 진단

다음 명령은 기존 체크포인트를 읽어 로그와 전이 보상을 대조하고, 환자 1명·병원
2개의 작은 환경에서 새 진단용 에이전트를 메모리 안에서 학습한다. 기존 모델과
학습 로그는 변경하지 않는다. 출력은 실행별 `results/diagnostics/`에 저장한다.

```powershell
.venv/Scripts/python.exe -B -u CODE/diagnose_learning.py --checkpoint results/training/checkpoint_v4_9fcc8308c8f256a7.pth --episodes 1200 --seeds 42,43,44 --evaluation-cases 256
```

실제 관측 벡터·마스크·보상·전이 수집기·DQN을 사용하되, 이동시간은 고정 규칙으로
생성하고 병원 순서를 무작위로 바꾼다. 따라서 기본 학습 경로를 점검하는 도구이며
SUMO의 동시 이송 성능이나 최단시간 정책 대비 우수성을 검증하는 도구는 아니다.
보상 감사는 결과가 관측된 선택 구간과 원래 환자의 선택 구간을 구분한다.
다른 환자의 선택 구간에 관측된 보상도 현재 설계에서는 정상적인 시스템 보상이므로,
그 비율만으로 구현 오류를 판단하지 않는다.

실행 결과 및 해석: [v4 36회 모델 진단](docs/diagnosis_v4_36_2026_11_10.md).

복수 환자의 결과 관측 시점과 완료 순서를 통제하는 후속 실험:

```powershell
.venv/Scripts/python.exe -B -u CODE/diagnose_overlap.py --checkpoint results/training/checkpoint_v4_9fcc8308c8f256a7.pth --decisions 3600 --seeds 42,43,44 --evaluation-episodes 256
```

이전 선택 정보 한 개를 관측에 보충하는 대조군:

```powershell
.venv/Scripts/python.exe -B -u CODE/diagnose_overlap.py --checkpoint results/training/checkpoint_v4_9fcc8308c8f256a7.pth --decisions 3600 --seeds 42,43,44 --evaluation-episodes 256 --profiles overlap_3,overlap_3_history
```

각 조건의 선택 수·실제 업데이트 수·탐색률을 맞추고, 모든 행동 조합을 열거한
할인 누적 보상 최적값도 비교한다. 이 진단에서만 타깃 동기화는 100회 업데이트마다
수행한다. 기존 SUMO 학습 설정을 바꾸는 명령은 아니다.
`overlap_3_history`는 원래 0인 관측 14번에 이전 선택 환자들의 미관측 보상 합/100을
넣는 실험용 조건이다. 이 작은 환경은 보상이 선택 시점의 입력으로 정확히 계산되지만,
실제 교통 환경의 미래 이송 결과는 알 수 없으므로 그대로 적용할 수 없다.
후속 실험 결과와 한계: [복수 환자 통제 실험](docs/overlap_diagnosis_2026_11_10.md).

### 실험 버전 5: 실제 운행 중 임무의 예상 보상 관측

통제 실험의 과거 선택 정보 보강을 실제 엔진에 적용하는 실험용 버전입니다.
추가 특징은 **현재 운행 중 임무들의 배정 당시 예상 환자 보상 합/100** 하나이며,
보상 버전 4, 선택 구간 전이 방식, 할인율, 학습률 등은 유지합니다.

```text
각 임무의 예상 총 시간 = 배정 당시 대기시간 + 배정 당시 예상 이동시간
각 임무의 예상 보상   = 보상 v4(예상 총 시간, KTAS, 선택 병원, 예약 전 점유율)
관측[15]             = sum(운행 중 각 임무의 예상 보상) / 100
```

예상값은 배정 때 고정하며, 실제 미래 도착시간이나 결과 보상을 읽지 않습니다.
임무가 도착·실패로 종료되면 운행 목록에서 제거되어 합계에서도 빠집니다.
현재 새로 선택할 환자는 아직 합계에 포함하지 않습니다. 실제 결과 보상은
기존처럼 완료 시점의 선택 구간에만 들어가므로 예상 보상이 중복 지급되지 않습니다.
예측이 실제 결과와 다를 수 있고, 이 특징 하나로 완전한 Markov 관측을 보장하지 않습니다.

새 상태 스키마는 4, 네트워크는 `hospital_shared_v5`, 기본 9병원 입력은 97차원입니다.
기존 v3/v4 모델은 원래 상태 차원과 네트워크로 계속 평가할 수 있지만 v5로
`--resume`할 수 없습니다. 기존 결과를 보존하고 새 실험으로 시작합니다.

예상 보상 특징을 사용하는 초기 실험:

```powershell
.venv/Scripts/python.exe -u CODE/train_agent.py --episodes 18 --eval-every 9 --ambulances 10 --virtual-count 2 --virtual-strategy far --placement-seed 42 --seed 42 --curriculum 0.1,0.3 --cycle-curriculum --validation-demand-levels 0.1,0.3 --validation-seeds 30001 --pending-reward-feature estimate --trace-decisions --quiet
```

정보 추가의 효과를 분리하는 대조 실험은 같은 명령에서
`--pending-reward-feature zero`로 바꿉니다. 두 조건 모두 97차원·동일한 네트워크를
사용하고, 대조군의 관측[15]만 0으로 고정합니다. manifest와 파일 해시가 달라
서로 덮어쓰지 않습니다. 같은 시드·부하·학습 예산·검증 패널로 비교해야 합니다.
이는 합성 환경 실험이며 실제 성능 향상은 아직 확인되지 않았습니다.

환자 결과 로그의 `estimated_reward_at_dispatch`,
`estimated_total_seconds_at_dispatch`와 실제 `reward`, `total_seconds`를 비교하면
배정 당시 예측 오차도 확인할 수 있습니다.

구현 범위와 호환성·검증 결과: [v5 관측 변경 기록](docs/v5_observation_2026_11_11.md).
