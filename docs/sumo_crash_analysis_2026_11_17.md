# SUMO 네이티브 충돌: 덤프 분석과 동일 조건 재현 (2026-11-17)

기존 Windows minidump의 읽기 전용 분석과, 보존한 체크포인트 사본에서 같은 학습 조건으로 실행한 진단 결과를 정리했습니다. SUMO 설치·차량 이동 규칙·수요·학습 설정은 유지했습니다. 원본 모델·manifest·덤프와 기존 학습 이력은 수정하지 않았습니다.

**후속 시험 결과:** 별도로 준비한 SUMO 1.28.0에서는 같은 다음 에피소드 25가 3,601초까지 완료되었고, 환자 26명 모두 도착했습니다. 원본과 분리한 학습 재개 명령은 [SUMO 1.28.0 검증·재개 안내](sumo_128_resume_2026_11_17.md)에 정리했습니다. 아래 내용은 기존 1.27.1의 충돌 분석 기록입니다.

**이후 실제 학습에서는 SUMO 1.28.0도 27회차에 다시 중단되었습니다.** 26회·342 업데이트는 저장되어 있으며, 진단 사본에서도 접근 위반을 재현했습니다. 최신 추적 결과와 배경 구급차 입력 검증은 [27회차 추가 분석](sumo_128_episode27_analysis_2026_11_17.md)을 참고해 주세요.

## 동일 조건 재현 결과

체크포인트 24회·292 업데이트를 복사하고 replay·optimizer·탐색률·RNG를 복원해, 에피소드 25·시나리오 7·시드 10067을 실행했습니다. 진단 중 메모리에서 학습은 진행되지만 가중치는 저장하지 않습니다.

| 항목 | 확인 결과 |
|---|---|
| 마지막 정상 시뮬레이션 시각 | 1,300초 |
| 실패한 명령 | 다음 `traci.simulationStep()` |
| SUMO 프로세스 종료 코드 | `3221225477`, 즉 `0xc0000005` |
| Python 후속 오류 | `FatalTraCIError: Connection closed by SUMO.` |
| 완료 / 발생 예정 환자 | 12 / 26명 |
| 직전 활성 차량 | `amb_e_14`, `amb_e_15` |
| 기존 실패 실행과 차량 완료 기록 | XML로 비교한 `tripinfo` 1,324개가 모두 일치 |
| 원본 체크포인트·manifest 해시 | 실행 전후 동일 |
| 원본에 남아 있는 학습 | 24회 완료, 업데이트 292회 |

직전 두 구급차는 모두 병원 `A1100141`로 이동 중이었습니다. 이는 직전 상태 기록이며, 특정 차량이나 병원이 충돌의 원인이라는 증거는 아닙니다. native stdout·stderr와 SUMO 오류 파일은 비어 있었고, 오류 메시지를 기록하기 전에 엔진이 종료된 상황과 일치합니다.

새 실행의 접근 위반 종료 코드와 동일한 시뮬레이션 출력은 확인했습니다. 새 minidump는 확인되지 않았으므로, 아래의 정확한 명령 주소·NULL 포인터 해석은 기존 덤프에서 얻은 근거로 구분합니다.

- [재현 증거](../results/diagnostics/sumo_crash_20261117_151920_cb3e1b/reproduction_proof.json)
- [진단 실행 요약](../results/diagnostics/sumo_crash_20261117_151920_cb3e1b/diagnostic_summary.json)
- [SUMO 종료·마지막 명령·설정](../results/diagnostics/sumo_crash_20261117_151920_cb3e1b/sumo/episode25/sumo_failure.json)
- [직전 임무 상태](../results/diagnostics/sumo_crash_20261117_151920_cb3e1b/last_successful_state.json)

첫 진단 시도에서는 진단용 JSON을 매초 교체하던 중 OneDrive의 일시적인 파일 잠금으로 observer가 중단되었습니다. 이를 원래 SUMO 충돌로 집계하지 않았습니다. 상태를 메모리에 보관하고 종료 시 저장하도록 수정했으며, 기록 실패도 원래 시뮬레이션 오류를 덮지 않게 처리했습니다. 그 뒤 두 번째 진단에서 원래 SUMO 연결 종료를 재현했습니다.

## 추가한 진단 기능

- 공통 실행에서 `sumo.log`, `sumo_errors.log`, `sumo_command.json`을 해당 실행 폴더에 저장합니다.
- 상세 진단에서는 native stdout·stderr, TraCI 명령, 프로세스 종료 코드, 마지막 정상 시각과 활성 차량을 수집합니다.
- 예외 처리 중 메타데이터가 없거나 연결 정리가 실패해도 원래 시뮬레이션 예외를 보존합니다.
- 일반 실행에서는 추가 tick 조회·전체 차량 스캔·상세 명령 추적을 수행하지 않습니다. 상세 추적은 진단 실행에서만 켭니다.

전체 회귀 테스트 **269개**와 소형 실제 SUMO의 정상 평가·대기열 비교 검증이 통과했습니다. 테스트는 진단 코드의 정상 동작과 기존 동작 보존을 확인하며, 엔진 충돌이 해결되었다는 뜻은 아닙니다.

다음 명령으로 새 진단 폴더를 만들어 같은 다음 에피소드를 재현할 수 있습니다.

```powershell
.venv/Scripts/python.exe -B -u CODE/diagnose_sumo_crash.py `
  --checkpoint results/all_scenarios_normal15_yield_repeat_v6/training/checkpoint_v6_f560a1f65da40cc8.pth `
  --output-root results/diagnostics
```

이 명령은 체크포인트 사본에서 다음 에피소드 1회만 실행하고 모델 가중치를 저장하지 않습니다. 동일 오류를 재현하면 종료 코드 1과 `diagnostic_summary.json`의 `expected_disconnect_reproduced=true`를 확인하시면 됩니다. 생성된 `traci_trace.py`는 증거용으로 보관하며, 그 파일을 그대로 실행하면 내부에 기록된 출력 경로를 재사용할 수 있으므로 위 진단 명령으로 새 폴더를 사용해 주세요.

## 확정한 충돌 형태

`C:\Users\emaet\AppData\Local\CrashDumps\`의 `sumo.exe.*.dmp` **6개**에서 같은 형태의 충돌을 확인했습니다. 가장 이른 덤프는 2026-11-13에 생성되었고, 최근 두 덤프는 2026-11-17 14:35와 14:40의 종료에 대응합니다.

| 항목 | 확인값 |
|---|---|
| 예외 코드 | `0xc0000005` |
| 잘못된 접근 | 주소 `0x70`을 읽으려는 접근 |
| SUMO 모듈 내부 위치 | `sumo.exe + 0x4b6882` |
| 해당 시점 RAX | `0x0` |
| 실행 명령 | `mov eax, dword ptr [rax + 0x70]` |
| 기계 코드 | `8b 40 70` |

따라서 **SUMO 네이티브 코드가 NULL 포인터에서 0x70만큼 떨어진 필드를 읽으려다 종료된 것**까지는 확인할 수 있습니다. Python에서 보인 `Connection closed by SUMO`는 이 종료 뒤 연결이 끊기면서 나타난 후속 오류와 일치합니다.

[Microsoft의 접근 위반 설명](https://learn.microsoft.com/en-us/shows/inside/c0000005)에서도 예외 매개변수의 첫 값 0은 읽기 접근, 두 번째 값은 잘못 접근한 주소라고 정의합니다. 실제 덤프의 두 값은 `[0, 0x70]`입니다.

## 아직 특정하지 못한 내용

SUMO 실행 파일에는 COFF 심볼이 없고 덤프의 SUMO CodeView 레코드도 비어 있습니다. 설치 `bin` 폴더에 SUMO PDB가 없으며, 사용 가능한 `llvm-symbolizer`도 함수·소스 줄을 반환하지 못했습니다.

현재 근거만으로는 다음 항목을 확정할 수 없습니다.

- NULL 포인터가 속한 클래스·함수·소스 줄입니다.
- 특정 차량·도로·정차·재경로·차로 변경 사건 중 무엇이 그 상태를 만들었는지입니다.
- blue-light 또는 sublane 설정이 직접 원인인지입니다.
- 이후 모든 에피소드에서도 충돌이 발생하지 않는지입니다. 별도 1.28.0에서 해당 25회차가 완료된 결과는 후속 안내에 기록했습니다.
- 설치 손상이나 RAM 부족이 원인인지입니다.

WER `ReportArchive`의 하위 내용은 읽기 권한이 없었으므로 접근 권한 확대는 시도하지 않았습니다. 사용자 `Local/CrashDumps`의 원본 덤프는 읽을 수 있었습니다.

## 공식 변경 기록과의 대조

[SUMO 1.27.1 공지](https://newsroom.eclipse.org/news/community-news/eclipse-sumo-1271-now-available)는 1.27.0에서 생겼던 특이한 회전 차로의 sublane 충돌을 수정했다고 설명합니다. 현재 설치가 이미 1.27.1이므로 그 과거 수정 내용을 이번 오류의 원인으로 바로 연결할 수는 없습니다.

[공식 ChangeLog](https://sumo.dlr.de/docs/ChangeLog.html)의 1.28.0에는 sublane 주행 관련 추가 수정이 있지만, 이번 메모리 주소와 연결되는 근거는 찾지 못했습니다. 엔진 버전 비교는 후속 진단 선택지이며 현재 조건을 유지하는 재현을 대체하지 않습니다.

## 후속 조치 선택지

1. **다른 SUMO 버전의 별도 대조:** 기존 설치와 학습 파일을 보존하고 별도 엔진에서 같은 재현 입력을 시험하는 방법입니다. 해당 버전에서 해결된다고 미리 단정하지 않습니다. 엔진을 바꾼 결과는 기존 엔진의 실험과 구분해야 합니다.
2. **현재 버전의 심볼 빌드·세부 조건 추적:** NULL 객체의 함수·소스 줄을 특정하거나, 진단용 복사 실험에서 주행 조건을 분리하는 방법입니다. 준비 비용이 더 크지만 원인 지점을 좁히는 데 도움이 됩니다.

충돌을 숨기거나 에피소드를 건너뛰는 변경은 하지 않았습니다. 기존 1.27.1은 그대로 보존했으며, 후속 시험에서 **별도 1.28.0의 25회차 완료·격리된 재개 사본 준비**까지 확인했습니다. 이후 회차 전체의 무중단과 충돌 원인 함수까지 확인한 것은 아닙니다.
