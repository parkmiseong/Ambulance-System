# 구급차 이송 웹 대시보드

프로젝트 루트의 `start_dashboard.bat`를 더블클릭하면 로컬 서버와 브라우저가 열립니다.
기존 `.venv`와 SUMO 설치를 그대로 사용하며 추가 패키지는 필요하지 않습니다.

```powershell
.venv/Scripts/python.exe -B CODE/web_dashboard.py
```

기본 주소는 <http://127.0.0.1:8000>입니다. 포트가 사용 중이면 `--port 8001`,
브라우저를 자동으로 열지 않으려면 `--no-browser`를 지정하세요.
서버 터미널에서 `Ctrl+C`를 누르면 진행 중인 실행도 종료됩니다.

2026-11-13 전체 변경과 최종 점검은 [오늘 작업 최종 정리](final_summary_2026_11_13.md)를 참고하세요.

2026-11-14부터 새 CLI 학습도 강남 기준 시간당 수요를 기본으로 사용합니다. 이 문서의 ‘기존 CLI 고밀도 시나리오 보존’은 `--demand-profile legacy`를 통한 과거 실험 재현을 뜻합니다. 공통 환자 수 수정 위치와 전체 시나리오 학습 명령은 [README](../README.md#환자-발생률-수정과-19번-시나리오-학습-2026-11-14)에 정리했습니다.

## 화면과 조작

- 왼쪽: 프로젝트의 강남 SUMO 도로망, 실제 구급차 위치, 병원 아이콘, 대기 환자, 병원 점유율.
- 지도는 드래그와 휠로 이동·확대하며 병원 아이콘이나 병원 목록을 누르면 상세 정보가 표시됩니다.
- 오른쪽: 시뮬레이션·학습 모드, 독립적인 시나리오 3개, 실행·일시정지·재개·중지, 배속 조절.
- **실행 설정** 제목의 접기·펼치기를 누르면 설정 항목을 숨기거나 다시 표시합니다. 접어도 배속·실행 버튼·진행 상태는 보이며, 새로고침해도 접힘 상태를 유지합니다. 초기화하거나 잘못된 입력을 수정해야 할 때는 자동으로 펼칩니다.
- 아래: 현재 에피소드의 보상 합계, 환자당 보상, 골든타임 내 도착 비율, 실패 수, 그래프와 보상 항목별 합계.
- 세부 설정: 환자 발생 기간, 구급차 수(1~10), 학습 에피소드 수, 랜덤 시드.
- **가상 병원 수**는 0개 또는 2~10개로 조절합니다(기본 2개). `−`·`+` 버튼 또는 숫자 입력을 사용하며, 0개는 실제 병원만 사용합니다. 생성할 때는 권역응급의료센터 2개가 기본 포함되고 나머지는 아래 유형 비율로 배분합니다.
- 보상 패널의 다운로드 아이콘은 현재 실행 상태와 완료된 에피소드 결과를 JSON으로 내려받습니다.
- 보상 아래의 상세보기 링크로 **환자별 이송 결과**로 이동합니다. 중증도별 집계, 병원×KTAS 도착 환자 분포와 전체 환자 기록을 볼 수 있습니다.
- 에피소드·중증도·병원·결과·환자/차량 ID로 필터링하고 **상세**에서 배정 시 병원 상태·시간·보상 분해를 확인합니다.
- **상세 CSV**는 현재 필터에 맞는 모든 환자를 내보냅니다. **결과 불러오기**에서는 이전 대시보드 실행도 조회할 수 있습니다.
- 지도에서 구급차를 누르면 환자 중증도와 목적지가 표시됩니다. 중증도 색상을 지도와 결과표에서 공통으로 사용합니다.
- 119/소방 지점을 참고 위치로 표시합니다. 현재 차량은 환자 위치에서 출발하므로 센터 출발 시뮬레이션을 뜻하지 않습니다.
- **구급차 우선 통행·양보**는 기본 ON입니다. 주변 차량을 실제 SUMO 위치에 표시하며 양보 중인 차량은 황색으로 구분합니다. **구급차 포커싱**에서 차량을 선택하면 차로 안에서 비키는 모습을 가까이서 계속 볼 수 있습니다.

## 가상 병원 유형 비율

**실행 설정 → 가상 병원 수** 아래에서 나머지 병원의 상대 비율을 입력합니다. 권역응급의료센터 2개는 비율 계산에서 제외하고, 남은 수를 지역응급의료센터·지역응급의료기관·응급실운영신고기관에 배분합니다. 실제 병원의 유형은 변경하지 않습니다.

초기 비율은 **5:4:1**이며 통계 추정치가 아닌 조절 가능한 시뮬레이션 초기값입니다. 각 값은 0~100의 정수이고 합계가 100일 필요는 없습니다. 추가 병원이 있으면 하나 이상의 비율이 0보다 커야 합니다. 가상 병원 0개는 생성하지 않으며, 1개는 기본 권역 2개 조건 때문에 허용하지 않습니다. `+`·`−`는 0개와 2개 사이를 건너뜁니다.

| 총 가상 병원 | 추가 유형 비율 (지역센터:지역기관:신고기관) | 최종 유형 수 (권역/지역센터/지역기관/신고기관) |
|---:|---|---|
| 2개 | 5:4:1 | 2 / 0 / 0 / 0 |
| 5개 | 1:1:1 | 2 / 1 / 1 / 1 |
| 10개 | 5:4:1 | 2 / 4 / 3 / 1 |

병원 수는 정수여야 하므로 가장 큰 나머지부터 배정해 총수를 정확히 맞춥니다. 동률은 위 유형 순서로 처리합니다. 위치별 추가 유형 배치는 별도 고정 시드로 섞어 같은 설정에서 재현되며, 기존 위치·ID·도로 검증은 보존합니다. 화면에서 **생성 예정**과 **현재/직전 실행 생성**의 실제 개수를 확인할 수 있습니다.

병원 이름만 바꾸는 것이 아니라 실제 `type`을 변경하므로 기존 환자 적합도·수용 판단·DQN 관측·보상에도 해당 유형이 반영됩니다. 총수가 같은 저장 DQN에서 유형만 바꾸면 병원 위치·순서·경로는 유지하고 유형 특징만 갱신합니다. 원본 모델 가중치는 변경하지 않습니다. 새 학습 manifest의 `web_virtual_hospital_mix`, 실행·에피소드 JSON의 `virtual_hospital_mix`에 비율·정수 배분·시드·실제 개수를 저장합니다. 기존 CLI의 가상 권역 병원 배치 기본값은 유지합니다.

검증 명령은 테스트 서버에서 `node tests/dashboard_browser_check.mjs --hospital-mix-only`이며 결과는 `results/verification/web_dashboard/hospital-mix-check.json`입니다.

## 구급차 선택과 카메라 추적

1. 학습 또는 시뮬레이션을 시작하고 실제 운행 중인 구급차가 나타나면 지도 위 **구급차 포커싱**을 누릅니다.
2. 목록의 **구급차 1, 구급차 2, …** 중 한 대를 선택합니다. 각 항목에는 KTAS와 환자 ID도 표시됩니다.
3. 카메라가 선택한 차량을 확대하고, 실제 SUMO 위치를 따라 계속 이동합니다. 다른 구급차를 선택하면 추적 대상도 바뀝니다.
4. **추적 해제**, 지도 드래그, **전체 보기**, 병원 목록 선택으로 자유 탐색으로 돌아갑니다. 확대·축소와 목록 닫기는 추적을 유지합니다.

운행 중인 차량만 목록에 표시하며 신호 대기 등 잠시 정차한 이송 차량도 포함합니다. 번호는 이송 차량 ID에 대응해 해당 회차에서 유지됩니다. 선택한 차량이 도착·실패 등으로 사라지면 추적을 해제하며 다른 차량을 자동 선택하지 않습니다. 일시정지하면 카메라도 해당 위치에서 멈추고, 새 실행이나 다음 에피소드에서는 추적 대상을 초기화합니다. 화면을 새로고침하면 추적 대상은 다시 선택합니다.

지속 추적 중 도로망 전체를 매 프레임 다시 그리지 않도록 여백이 있는 지도 이미지를 이동해 재사용합니다. 구급차와 주변 차량은 별도의 실제 좌표로 갱신합니다.

## 병원별 혼잡 비율 보상

웹의 새 학습과 시뮬레이션은 **여유 병원 가점·혼잡 병원 감점** 방식(`balanced`)을 사용합니다. 시나리오의 여유·보통·혼잡은 초기 배경 점유율 범위를 정할 뿐이며, 실제 점수는 **선택한 병원의 배정 직전 점유율**로 개별 계산합니다. 현재 웹의 `arrival` 방식은 배경 환자·치료 중 환자를 포함하고 이동 중인 환자의 병상을 예약하지 않습니다. 재이송 시에는 최종 목적지를 다시 선택한 시점의 비율을 사용합니다. 기존 예약 방식에서의 점유율은 다른 이송의 예약 병상도 포함합니다. 도착 후 수용 판정은 별도로 도착 당시 비율로 처리합니다.

```text
o = 배정 직전 해당 병원의 점유율 (0~1)
병원 혼잡도 보상 = 8 × (1 - 2o) - 5 × max(o - 0.7, 0) / 0.3
```

| 해당 병원 점유율 | 혼잡도 보상 |
|---:|---:|
| 20% | +4.80점 |
| 50% | 0점 |
| 60% | -1.60점 |
| 70% | -3.20점 |
| 80% | 약 -6.47점 |

50%를 기준으로 연속적인 가점·감점을 주고 70% 초과 시 기존 과밀 감점을 추가합니다. 기준과 가중치는 연구용 설계값입니다. 이 값은 환자 총 보상의 한 항목이며 골든타임·소요 시간·병원 적합도·거절 비용과 함께 반영합니다. 실제 치료 역량·수용 가능 여부 필터는 계속 적용됩니다.

병원 현황에는 **현재 비율 기준 참고 점수**, 환자 상세에는 **배정 시 비율과 실제 적용 혼잡도 보상**을 표시합니다. 현재 비율은 배정 이후에도 변하므로 두 점수가 다를 수 있습니다. 보상 패널의 ‘병원별 혼잡도’는 결과 확정 환자의 점수를 합산합니다. CSV·JSON에도 기록하며, 기존 점유율·과밀 항목을 다시 더해 중복 합산하지 않습니다. 기본 보상 v4에서 이송 실패는 실패 비용으로 대체하므로 혼잡 가점도 주지 않고, 관측 종료에도 혼잡 가점을 부여하지 않습니다.

새 방식은 `config.congestion_reward_mode=balanced`, `run.json`의 `hospital_congestion`에 저장합니다. 기존 CLI 기본값과 과거 manifest는 `penalty`로 복구해 원래 점수를 재현합니다. CLI에서 새 방식을 쓰려면 학습·평가 옵션에 `--congestion-reward balanced`를 추가합니다. 이어서 학습할 때도 원래와 같은 방식을 지정합니다. 방식이 다른 평가는 한 집계·최종 비교에 섞지 않습니다. 과거 모델을 새 방식으로 평가할 수 있지만 가중치가 자동으로 새 보상을 학습하는 것은 아닙니다.

검증 명령은 `.venv/Scripts/python.exe -B tests/verify_hospital_congestion.py`와 별도 서버의 `node tests/dashboard_browser_check.mjs --congestion-only`입니다. 실제 SUMO에서 기존과 동일한 3명 이송에 +4.8·+3.2·+1.6점이 각각 반영되고, 혼잡 병원에는 감점이 적용되며 DQN 학습 보상 합계가 일치함을 확인합니다.

## 강남 기준 환자 발생률

환자 수 기준은 강남구의 [제40회 강남통계연보(2024년 기준)](https://www.gangnam.go.kr/board/B_000645/1068850/view.do?mid=ID02_01020902) 6쪽의 **119 구급활동 46.6건/일**입니다. 이를 24로 나눈 1.9417건/시간을 수요의 대리 기준으로 삼고, 보통은 10%만 높인 2.1358명/시간으로 설정했습니다. 구급활동 1건을 가상 환자 1명으로 대응한 가정이며, 실제 전체 환자 수나 이송 인원 수의 직접 측정값은 아닙니다. 연평균 기준으로 시간대별 변동은 모델링하지 않습니다.

기본 발생 기간은 3,600초(시뮬레이션 1시간), 최대 86,400초(24시간)입니다. 초당 확률은 `시간당 수요 / 3600`이고 기대 인원은 `시간당 수요 × 기간 / 3600`입니다. 실제 발생 수는 시드에 따라 달라져 짧은 실행에는 0명일 수 있습니다. 화면에서 시간당 수요와 선택 기간의 기대 인원을 확인할 수 있습니다. 근거와 배율은 `DATASET/gangnam_ems_reference.json`, 변환은 `CODE/dashboard_demand.py`에 기록했습니다. 기존 CLI의 고밀도 시나리오와 저장 실험의 재개 조건은 그대로 유지합니다.

## 환자 수 직접 입력

실행 설정의 **환자 수 설정**에서 발생 방식을 선택합니다.

| 방식 | 입력 예시 | 결과 |
|---|---|---|
| 강남 기준 · 3단계 | 보통 | 기존 약 2.14명/시간의 확률적 발생 |
| 시간당 환자 수 직접 입력 | 12.5명/시간 | 시뮬레이션 1시간당 기대 인원. 실제 수는 시드에 따라 달라짐 |
| 총 환자 수 직접 입력 | 20명 | 발생 기간 내 정확히 20명 발생. 시각은 시드에 따라 무작위로 배치 |

총 환자 수는 **회차당 인원**입니다. 학습 3에피소드에서 20명으로 지정하면 학습 환자는 총 60명이며, 별도 검증에서도 매번 20명이 발생합니다. 검증 환자는 화면의 전체 학습 인원에 합산하지 않습니다. 지정한 수는 발생 환자 수이며 이송 성공 수를 보장하지는 않습니다.

시간당 직접 입력은 0~3,600명/시간이며 소수를 허용합니다. 고정 총 인원은 0명부터 발생 기간의 초수까지 정수로 지정합니다. 현재 엔진은 초당 최대 1명을 생성하므로 발생 기간 60초에는 최대 60명을 지정할 수 있습니다. 기간은 **세부 실행 설정 → 환자 발생 기간**에서 바꿉니다. 두 방식 모두 0명을 명시할 수 있습니다.

사용자 입력에 강남 기준 배율을 추가로 곱하지 않습니다. 3단계 버튼을 누르거나 초기화하면 강남 기준으로 돌아갑니다. 실행 중에는 입력을 잠그며 새로고침하면 해당 실행의 설정을 복구합니다. 입력 방식·수치·고정 인원은 실행 기록과 새 학습 manifest에 저장합니다. 기존 CLI 시나리오의 확률과 난수 생성 방식은 유지합니다.

완료 직후에는 이전 작업 프로세스의 정리가 끝날 때까지 시작 버튼이 잠시 잠깁니다. 정리가 끝나면 새 환자 수로 다시 실행할 수 있습니다.

## 병원 수용 요청과 거절 패널티

웹의 **병원 도착 후 거절 패널티**는 기본 ON이며 새 학습과 시뮬레이션에 모두 적용합니다. 흐름은 **사전 수용 확인 → 가능한 병원으로 출발 → 실제 병원 도착 후 수용 판정**입니다. 사전에 병상 부족·수용 중단이 확인된 병원은 출발 후보에서 제외하며 거절 벌점을 주지 않습니다. 이동 중에는 병상을 예약하지 않으며, 실제 병원 접근 도로의 정차 지점에 도착했을 때 현재 병상과 `accepting` 상태를 확인합니다. 이때 수용을 거절한 경우에만 **1회당 -12점**을 부여합니다. 임의의 거절 확률은 추가하지 않습니다.

여러 구급차가 같은 병원의 사전 수용 가능 상태를 확인하고 이동하는 동안, 먼저 도착한 환자가 마지막 병상을 사용하면 나중에 도착한 환자는 거절될 수 있습니다. 거절 후에는 **같은 구급차 ID·같은 환자**를 유지하고 현재 병원 위치에서 다른 수용 가능한 병원까지 실제 SUMO 경로로 재이송합니다. 지도 포커싱도 같은 차량을 계속 따라갑니다. 대안이 없으면 현재 병원에 정차해 기다리며 상태 재확인만으로 벌점을 반복하지 않습니다. 그 병원이 수용 가능해지면 대기 후 수용할 수 있습니다. 최초 출발 이후 이동·재이송·병원 대기는 모두 이송 시간에 포함하며 이송 제한시간도 최초 출발부터 계산합니다. 출발 전 대기는 별도로 기록합니다.

경로·치료 역량에 따른 사전 제외에는 벌점이 없습니다. 출발 전 가능한 병원이 없으면 기존 최대 배정 대기시간까지 기다립니다. 사전 연락 자체의 통화 시간과 외부 신규 환자의 별도 무작위 유입은 모델링하지 않습니다. 배경 점유율과 이 시뮬레이션의 다른 환자 입원·치료 종료로 병상이 변합니다. 사전 확인은 현실 절차를 단순화한 가정이며 확정 예약과 구분합니다. [보건복지부 이송체계 안내](https://mohw.go.kr/gallery.es?act=view&bid=0003&list_no=379887&mid=a10605040000&tag=)는 사전 정보 공유·수용 확인, 중증도별 절차와 긴급 이송 예외를 설명합니다.

거절 시점에 -12점을 학습 전이에 즉시 반영하고 환자별 최종 보상에도 포함합니다. 최종 결과를 학습에 반영할 때 이미 지급한 거절 비용은 다시 지급하지 않습니다. 성공·실패 모두 `reward_components.rejection`에서 거절 비용을 분리해 볼 수 있습니다. 기본 보상 v4에서 최종 이송 실패 비용은 -85점이며, 거절 2회 후 실패하면 **-85 -24 = -109점**입니다. 관측 시간 경계로 종료되면 실패 비용은 붙이지 않지만 이미 발생한 거절 비용은 유지합니다.

보상 패널에는 실제 도착 후 수용 거절 횟수와 별도 **수용 거절** 항목을 표시합니다. 결과 확정 전에도 거절 비용은 누적 보상에 반영합니다. 실행 중 환자당 보상과 골든타임 비율은 결과 확정 환자 기준입니다. 환자 상세에는 실제 방문 병원의 순서·출발/도착 시각·도착 시 점유율·수용 결과·같은 구급차 ID가 표시됩니다. 거절 이력에는 `stage=after_arrival`, 실제 도착·거절 시각과 사유·점수를 저장하며 CSV·전체 JSON에도 포함합니다. `experiment_history.csv`의 `hospital_rejection`은 사건 기록이고, 해당 비용은 환자 최종 보상에도 들어 있으므로 다시 합산하지 않습니다. 최종 수용된 병원만 이송 완료 집계에 포함합니다.

새 방식은 `config.admission_mode=arrival`로 구분합니다. OFF와 기존 CLI 기본값은 과거 사전 검사·예약(`precheck`) 방식입니다. 이전 `request`는 출발 전 문의 거절을 벌점으로 처리하던 과거 실험 재현용으로 남깁니다. CLI에서 도착 후 판정을 활성화하려면 `--admission-mode arrival`을 지정합니다. 과거 모델에 옵션을 켜는 것은 새 조건에서의 평가이며, 가중치가 자동으로 새 동작을 학습하지는 않습니다. 수용 방식이 다른 평가는 한 집계·최종 비교에 섞지 않습니다.

```powershell
# 새 CLI 학습의 다른 옵션과 함께 사용
.venv/Scripts/python.exe -B CODE/train_agent.py --admission-mode arrival --congestion-reward balanced --output-root results/admission_arrival
# 기존 best를 도착 후 판정 조건에서 평가하는 경우
.venv/Scripts/python.exe -B CODE/run_scenarios.py --model results/v6_s6_updates_s42/models/dqn_v6_919eaa77a75fac3a_best.pth --admission-mode arrival
```

실제 SUMO 검증은 `.venv/Scripts/python.exe -B tests/verify_arrival_rejection.py`로 실행합니다. 3명 모두 최종 수용, 병원 정차 후 실제 거절 3회·-36점, 같은 차량의 물리적 재이송, 이동 중 예약 0건, 학습 보상 합계 일치를 `results/verification/arrival_rejection/proof.json`에 기록합니다. 과거 `verify_hospital_rejection.py`와 기존 `hospital_rejection/proof.json`은 출발 전 request 방식의 이력입니다.

브라우저 검증은 별도 서버에서 `node tests/dashboard_browser_check.mjs --rejections-only`로 실행합니다. 도착 이후의 거절 시각, 누적 보상·횟수, 환자 상세·CSV의 실제 병원 방문 순서와 차량 유지, OFF의 기존 방식 복귀를 확인합니다. 최신 결과는 `results/verification/web_dashboard/arrival-rejection-check.json`에 저장합니다.

## 장시간 배경 교통

장시간 실행과 환자 발생 종료 후의 이송 마무리 구간에서도 배경 차량 유입을 유지하기 위해 원본 1시간 승용차 trip을 3,600초 간격으로 반복합니다. **2026-11-16부터 새 CLI 학습도 웹과 같은 반복 규칙을 기본으로 사용합니다.** 원본 파일은 수정하지 않고 실행 폴더의 `background_repeated.trips.xml`에 나머지 구간을 생성합니다. 원본 경로·출발 속성은 보존하고 ID와 출발 시각만 바꿉니다. 시간대별 교통량 실측이 아닌 주기적 반복 가정입니다.

반복 여부는 공통 `config.repeat_background_traffic`에 저장하고 반복 규칙은 manifest의 `background_traffic`과 실험 signature에 포함합니다. 실제 원본 파일 해시·반복 주기·생성 수는 실행 결과에 남깁니다. CLI에서 `--no-repeat-background-traffic`를 지정하면 반복을 끌 수 있습니다. 과거 CLI 모델은 원래 반복 OFF를 복원하고, 과거 웹 모델은 저장된 반복 메타데이터를 근거로 원래 동작을 복원합니다. 기존 모델의 조건을 바꾸어 추가 학습하지 않고 새 실험으로 구분합니다.

## 웹 모델의 CLI 평가와 결과 보관

웹 best를 CLI로 평가할 때는 기본 `--scenario-profile saved`로 웹에서 저장한 환자 수요·시나리오·고정 환자 수·초기 점유율을 복원합니다. `--scenario`를 생략하면 저장된 웹 시나리오를 그대로 사용합니다. 웹의 세 단계 기본 수요를 사용한 모델에서 `--scenario N`을 지정하면 해당 단계의 저장된 발생률을 사용하며, 직접 입력한 시간당 발생률 또는 고정 총 환자 수는 유지하면서 시나리오 ID·교통 단계를 변경합니다. 기존 CLI 시나리오 정의로 전환하려는 경우에만 `--scenario-profile standard`를 명시해 주세요.

```powershell
.venv/Scripts/python.exe -B CODE/run_scenarios.py `
  --model results/web_dashboard/<실행_ID>/models/<모델명>_best.pth `
  --strategies shortest_time,heuristic,dqn --quiet
```

`<실행_ID>`와 `<모델명>`은 실제 저장 경로로 바꾸어 주세요. 위 명령은 웹 화면에서 새 조건을 골라 시뮬레이션하는 것과 구분됩니다. 웹 화면에서는 선택한 실행 설정이 우선하며, 학습 당시 조건과 다른 수요·병원·점유율 등의 실험도 가능합니다.

CLI 평가와 대기열 비교는 선택한 best와 manifest를 해당 웹 실행 폴더의 `evaluations/<평가 실행 ID>/`에 복사한 뒤 사본을 사용합니다. 모델·manifest의 SHA256과 실제 평가 환경의 fingerprint를 함께 기록하므로, 원본 best가 이후 갱신되어도 평가한 모델을 확인할 수 있습니다. 동일 조건의 최종 모델 비교와 교수님께 전달할 자료 구성은 [학습·평가 재현성 안내](evaluation_reproducibility_2026_11_16.md)를 참고해 주세요.

## 구급차 양보

웹 DQN 시뮬레이션은 실행 폴더의 `evaluation_snapshot/`에 best·manifest 사본과 SHA256을 보관한 뒤 사본을 사용합니다. `run.json`과 에피소드 JSON에는 모델 사본 정보와 화면에서 실제로 적용한 환경의 fingerprint를 기록합니다. 학습 원본 모델은 수정하지 않습니다.

웹 실행에서 ON이면 SUMO `ambulance_custom`에 blue-light 장치를 부착하고 `--lateral-resolution 0.4`로 차로 내 횡방향 이동을 활성화합니다. 반응 거리는 60m입니다. 같은 진행 방향의 맨 왼쪽 차로 차량은 왼쪽, 나머지 차로 차량은 오른쪽으로 비켜 통로를 형성합니다. 도로 폭·교통 밀도·반응 확률에 따라 양보 가능 여부와 시점은 달라집니다.

이 옵션에는 SUMO blue-light의 적색 신호 특례와 긴급 차로 변경도 포함됩니다. ON/OFF 비교는 이 우선 통행 기능 묶음에 대한 비교이며 양보만의 독립 효과를 뜻하지 않습니다. [SUMO 긴급차량 문서](https://sumo.dlr.de/docs/Simulation/Emergency.html), [차로 내 이동 모델 문서](https://sumo.dlr.de/docs/Simulation/SublaneModel.html)를 따릅니다.

지도는 운행 중인 연구용 구급차 주변 100m 내 차량을 최대 150대 표시합니다. SUMO의 `rescueLane` 값에 현재 연구용 구급차 ID가 포함된 차량만 **양보 중**으로 표시하며, 차량을 누르면 양보 대상 ID를 확인할 수 있습니다. ‘주변 양보’는 이 표시 범위의 수치입니다. 전체 도로망의 양보 차량 수나 누적 수가 아닙니다. 일반 차량을 장식용으로 생성하거나 화면에서 임의로 움직이지 않습니다.

선택값과 반응 거리·횡방향 해상도·신호 특례 포함 여부는 `run.json`, 에피소드 결과와 새 학습 manifest에 저장됩니다. 학습과 고정 검증에도 같은 ON/OFF 설정을 적용합니다. 기존 모델로 양보를 켜서 평가할 수 있으나 학습 당시와 교통 조건이 달라질 수 있습니다. **2026-11-16부터 새 CLI 학습도 웹과 동일하게 ON이 기본**이며 `--no-emergency-yield`로 끌 수 있습니다. CLI 평가는 모델에 저장된 설정을 복원하며, `--emergency-yield` / `--no-emergency-yield`로 명시적으로 바꿀 수 있습니다. 기존 CLI 모델은 OFF, 과거 웹 모델은 `web_emergency_yield`의 선택값을 유지합니다. 새 manifest는 `config.emergency_yield`와 공통 `emergency_yield` 매개변수도 signature에 포함하므로 OFF 학습을 ON 조건으로 바로 재개할 수 없습니다. 횡방향 모델을 켜면 계산량이 늘어 실제 실행 배속은 낮아질 수 있습니다.

실제 SUMO 대조 검증은 `.venv/Scripts/python.exe -B tests/verify_emergency_yield.py`로 실행합니다. 2차로에서 양쪽 차량 이동, 구급차 통과, 정상 주행 복귀와 OFF 대조를 확인하며 `results/verification/emergency_yield/`에 관측값을 저장합니다.

`CODE/simulation.py`의 공통 `run_episode`를 사용하며 별도 장식용 애니메이션이나 가짜 보상은 없습니다.
지도 데이터는 로컬 SUMO 도로망에서 읽기 때문에 외부 지도 API나 인터넷이 필요하지 않습니다.
도로망 로딩과 초기 접근 경로 검증에 시간이 걸릴 수 있으며 준비 상태가 표시됩니다.

시뮬레이션은 저장된 **best** 모델, 도로망 최단거리, 최단시간, 종합 휴리스틱, 예상 보상 그리디 중 선택합니다.
best 모델은 `results/models`, `results/<실험>/models`, 대시보드 실행별 모델 폴더에서 찾습니다.
DQN 사용 시 원래 모델의 manifest로 병원 순서와 관측 설정을 복구합니다.
평가에서는 탐색과 학습을 끕니다. 처음에는 모델의 저장된 가상 병원 수를 사용하지만, 시뮬레이션에서도 숫자 입력과 `−`·`+`로 0개 또는 2~10개를 바꿀 수 있습니다. 수를 바꾸면 다음 실행에서 실제 도달 가능한 병원과 환자 출발 도로를 다시 검증하므로 준비에 시간이 더 걸립니다.

공통 병원 평가 구조의 v4·v5·v6 DQN은 학습된 가중치를 그대로 복사하고 새로운 병원 수에 맞는 관측·행동 크기로 평가합니다. 원본 모델 파일·manifest를 변경하거나 자동으로 재학습하지 않습니다. 학습 당시와 병원 집합이 다른 조건의 평가이므로 기존 구성에서의 성능과 같은 조건으로 해석하지 않습니다. 원래 병원 수·모델 서명·요청 수·변환 방식을 `run.json`과 에피소드 결과의 `hospital_transfer`에 남깁니다. 병원 수가 같으면 원래 구성과 순서를 그대로 복구합니다.

구형 `flat_v3` 모델은 입력·출력층이 병원 수에 고정되어 있어 수 변경을 지원하지 않습니다. 이 모델에서 변경하려면 공통 병원 평가 구조의 모델이나 다른 정책을 선택합니다. 규칙 기반 정책과 새 학습도 동일한 생성 수·유형 비율 설정을 사용합니다.

가상 병원 수 변경·차량 선택·추적 검증은 별도 테스트 서버에서 `node tests/dashboard_browser_check.mjs --tracking-only`로 실행합니다. 실제 시뮬레이션을 시작·중지하고 결과를 `results/verification/web_dashboard/hospital-tracking-check.json`에 저장합니다.

학습은 기존 모델을 덮어쓰지 않고 선택한 가상 병원 수를 포함한 새 v6 실험을 만듭니다.
v6 기본 학습 설정과 실제 공통 엔진을 사용합니다. 에피소드마다 last·전체 학습 상태 체크포인트를 저장하고,
실제 가중치 업데이트가 있고 별도의 고정 검증에서 환자가 발생한 경우에만, 탐색 없이 얻은 환자당 보상이 가장 높은 모델을 best로 저장합니다. 검증 환자가 없으면 평균 보상을 0점으로 해석하지 않고 평가 불가로 남깁니다. 검증 시드는 `기본 시드 + 50000`이며 manifest에 기록합니다.
학습 시작 후 만들어진 모델을 사용하려면 모델 목록의 새로고침을 누르세요.
짧은 실행은 replay 배치 32개를 채우지 못해 업데이트가 0회일 수 있습니다. 학습 모드에서 전체 기대 환자 수를 표시하고, 결과에서는 실제 누적 가중치 업데이트 수를 명시합니다. 기본 보통 수요·1시간·3에피소드의 기대 환자는 약 6.4명입니다. 학습량이 충분한지는 환자 수와 실제 업데이트 수를 함께 확인하세요.

배속은 학습·시뮬레이션의 지도 재생 시간에 적용됩니다. 학습 에피소드 사이의 고정 검증은
최대 속도로 처리하며 지도에서 종료된 학습 차량을 지우고 마지막 병원·보상 결과를 유지합니다. 검증 중에도 일시정지·중지가 가능합니다.
설정 배속은 목표 최대 속도이며 도로 경로 계산과 모델 학습 부하에 따라 실제 속도는 낮아질 수 있습니다.
환자 발생 기간이 끝나도 대기·운행 중인 환자의 결과가 확정될 때까지 실행합니다.
실행 중 골든타임 비율은 결과 확정 환자 기준이며 완료 후에는 전체 발생 환자 기준입니다.
시간 제한으로 관측이 종료된 환자는 실패와 구분해 결과 JSON에 `censored`로 저장됩니다.

모든 신규 결과는 `results/web_dashboard/<실행 ID>/`에 분리됩니다.
CSV 환자별 결과, 에피소드 JSON, 환자별 `patients_episodeN.json`, 모델·체크포인트, manifest, SUMO 출력을 포함합니다.
실행 중 중지하면 현재 에피소드의 일부 결과만 남고, 이미 완료된 에피소드와 모델은 보존됩니다.
이 대시보드는 한 번에 하나의 실행을 지원하며 기존 CLI 학습과 별도 프로세스를 사용합니다.

프로젝트의 연구용 보상·골든타임 가정을 그대로 표시합니다. 기본 화면의 `v6`는 학습 구현 버전이며
이전 best 모델을 선택하면 해당 모델의 원래 관측 버전으로 시뮬레이션합니다.
